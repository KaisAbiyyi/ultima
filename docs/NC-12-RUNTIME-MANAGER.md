# NC-12 — Verified managed Codex with staged startup and automatic rollback

**Default remains the user-selected system Codex.** Optional managed mode is explicitly triggered by desktop user controls; installing/staging bytes never activates the candidate or touches system Codex, PATH, npm globals, credentials, model permissions or workspace data.

## Three review blockers closed in this cloud scope

1. **NC-06 desktop integration:** `src-tauri/src/runtime.rs` and IPC commands `ultima_runtime_status/stage/activate/system/rollback` are invoked by the desktop bridge and optional actions in `src/Desktop.svelte`. Existing `ultima_connect` dynamically resolves the persisted managed selection via `ultima-runtime-manager`, otherwise launches the explicitly selected system binary. The entire connect/update path takes an async mutex and checks `SessionGate::require_idle()`: neither Running, Stopping nor Poisoned can perform mutations. The event/generation fence, shutdown sentinel and NC-07 approval refusal are preserved.
2. **Actual upstream asset provenance pin:** `protocol/managed-assets.json` records the *official GitHub release asset identity, exact platform target, URL, size and SHA-256* read from [official Codex rust-v0.164.0 release metadata](https://api.github.com/repos/openai/codex/releases/tags/rust-v0.164.0). Windows x64 reviewed asset `codex-x86_64-pc-windows-msvc.exe`: **SHA-256** `6f267830b029ee25d9339864aa867cd45de9f8fd4c5ea007d2e63c13a0c66d36`, **354,558,768 bytes**. This manifest is compiled into the trusted app build and can only change by source review. `Approval::new` no longer accepts arbitrary matching caller-provided hashes: it checks against a fixed reviewed pin and NC-11's supported `0.164.0` matrix. Wrong OS/architecture is **unsupported** (system Codex remains the default), as are unpromoted/newer tags, different release URLs, arbitrary checksums and modified assets. The local staged file is checked twice against the pin, pre and post copy. No automatically downloaded scripts, archives or unsigned external manifests.
3. **Bounded preflight and recovery:** the only production managed activation API is `activate_checked` which starts staged Codex under NC-04's trusted-root supervisor and Windows job containment, performs **unauthenticated** `initialize/initialized/model-list` on stdio JSONL with 18-second deadline, rejects malformed/error responses and inbound tool/approval requests, then stops and **reaps** the entire owned process before making any selection durable. A live managed session that fails to start or later fails its drive loop is stopped and rolled back to the prior recorded selection under the exclusive update mutex, *before SessionGate is released for a new connection*. No in-flight command or approval is replayed. If stop cannot be confirmed, the existing gate remains poisoned and reconnect is refused.

## Bounds, offline and failure modes

- Staging uses explicit absolute path selected by the user, a dedicated sentinel-marked Ultima-owned store and exclusive update lock. Limit **512 MiB binary**, **8 versions**, **128 immutable journal records**; refuse symlinks, unrelated directories, immutable-version replacement and corrupted state. No network is required for already pinned downloaded bytes.
- Rollback scans the immutable journal newest-first for a **different** previous selection: a managed candidate qualifies only when its version differs from the failing selection **and its current artifact digest/approval still verifies**. Consecutive duplicate records of the failing version are ignored. A prior System choice is a valid safe terminal fallback; if no eligible different verified runtime exists, select System. Calling rollback while System is already selected is **idempotent** (does not re-enable previously failed managed versions or append a redundant record). A corrupted journal fails closed; no unapproved or tampered candidate may be restored. Executable integrity is rechecked at every managed launch. Read-only preflight does not start a tool-executing turn. No background poller/process or implicit fallback process spawning. Changes to the official pinned version require NC-11 matrix + reviewed trust manifest and new application build.
- SHA-256 from official release API metadata is an immutable review pin, **not** Sigstore signature verification. Signed package, asset attestations/claim-by-claim provenance verification, real owner Windows process-tree RAM/p95 latency and product release readiness remain separate NC-13/NC-10 native/owner gates and are **NOT_RUN**.

## Cloud acceptance

Exact-head GitHub Actions: NC-12 Linux + hosted Windows fmt/Clippy/healthcheck/rollback/integrity/unit tests, NC-06 Windows Rust build and tests, frontend type-check/unit/build/E2E, NC-01 and NC-11 pinned protocol regression. The synthetic fake App Server runs only in tests, never as a deployed alternate engine. Hosted CI is **not** owner-native testing.

Security note: store is user-writable by design; hostile same-user concurrent filesystem mutation between final hash verification and OS executable mapping cannot be proven impossible by a SHA check. For stronger production guarantees, locked file handles and Windows Authenticode/Sigstore verification require separate release security acceptance.
